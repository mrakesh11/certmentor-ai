AWS Databases - Cloud Practitioner Cheatsheet

Relational Databases (OLTP)
Amazon RDS
Type: Relational Database Service for OLTP (Online Transaction Processing)
Engines: MySQL, PostgreSQL, MariaDB, Oracle, SQL Server, IBM Db2
Use Case: Traditional applications, ERP, CRM, e-commerce
Scaling: Vertical scaling (increase instance size)
Cost Metric: Instance hours, storage, I/O operations, backup storage
Remember: RDS is managed (AWS handles patching, backups, high availability), but not serverless (you provision and pay for instances even when idle).
Amazon Aurora
Type: AWS-proprietary relational database with MySQL/PostgreSQL compatibility
Benefits: 5x performance of MySQL, 3x of PostgreSQL
Storage: Auto-expanding from 10GB to 128TB
Replicas: Up to 15 read replicas with sub-10ms replica lag
Cost Metric: Pay for compute and storage used (more efficient than RDS)
Think: "Aurora is AWS's premium version of MySQL/PostgreSQL" with superior performance, availability, and cost efficiency.

NoSQL Databases
Amazon DynamoDB Serverless
Type: Key-Value and document database
Performance: Single-digit millisecond latency
Scaling: Automatic scaling with no downtime
Capacity: Provisioned or On-Demand capacity modes
Cost Metric: Provisioned read/write capacity or pay-per-request
Remember: DynamoDB is fully serverless (no servers to manage), infinitely scalable, and integrates natively with Lambda for event-driven architectures.
DynamoDB Accelerator (DAX)
Type: In-memory cache for DynamoDB
Performance: Reduces response times from milliseconds to microseconds
Use Case: Read-heavy workloads or requiring microsecond latency
Cost Metric: DAX node-hours (similar to ElastiCache)
Think: "DAX is to DynamoDB what ElastiCache is to RDS" - it's an in-memory acceleration layer.
Amazon DocumentDB
Type: Document database with MongoDB compatibility
Nickname: "Aurora for MongoDB"
Data Format: JSON documents (NoSQL)
Scaling: Scale compute and storage separately
Cost Metric: Instance hours, storage, I/O operations
Think: "If you want MongoDB but fully managed by AWS with the same architecture benefits as Aurora."
In-Memory Databases
Amazon ElastiCache
Type: In-memory cache for data caching
Engines: Redis and Memcached
Use Case: Real-time applications, caching, session stores, gaming leaderboards
Cost Metric: Node-hours, data transfer
Remember the key differences:
- Redis: Advanced data structures, persistence, replication
- Memcached: Simple object caching, multi-threading, no persistence
Data Warehousing & Analytics
Amazon Redshift
Type: Data Warehouse for OLAP (Online Analytical Processing)
Query: SQL-based for analytics
Performance: 10x faster than traditional warehouses with columnar storage
Size: Petabyte-scale
Cost Metric: Node-hours, backup storage
Key difference from RDS: OLAP vs. OLTP - Redshift is for analyzing massive datasets, not processing transactions.
Amazon Athena Serverless
Type: Interactive query service for S3 data
Query: Standard SQL
Use Case: One-time queries, data exploration, analyze logs
Cost Metric: Pay per query / TB scanned
Think: "SQL queries directly on S3 data without loading into a database first. Perfect for ad-hoc analysis."
Amazon EMR (Elastic MapReduce)
Type: Managed Hadoop framework
Tools: Hadoop, Spark, HBase, Presto, Flink
Use Case: Big data processing, machine learning, predictive analytics
Cost Metric: EC2 instance hours + storage
Remember: EMR is for batch processing massive datasets using open-source tools, but you still manage clusters.
Amazon QuickSight Serverless
Type: Business Intelligence & visualization service
Integration: AWS data sources, on-premises databases
Use Case: Dashboards, interactive reports, embedded analytics
Cost Metric: Per user/month or per session
Think: "Last mile of your data pipeline - turns raw data into meaningful visualizations for business users."
Specialized Databases
Amazon QLDB (Quantum Ledger Database)
Type: Immutable transaction ledger database
Key Feature: Cryptographically verifiable transaction history
Use Case: Financial records, supply chain, insurance claims, registrations
Cost Metric: Storage used + I/O operations
Think: "When you need a trusted, immutable history of all data changes with built-in verification."
Amazon Managed Blockchain
Type: Managed blockchain network service
Frameworks: Hyperledger Fabric & Ethereum
Use Case: Multi-party applications, decentralized transactions
Cost Metric: Network resources, storage, data processing
Remember: For decentralized applications where multiple parties need to share data without a central trusted authority.
Amazon Neptune
Type: Graph database service
Query: Gremlin, SPARQL, openCypher
Use Case: Knowledge graphs, social networks, fraud detection, recommendation engines
Cost Metric: Instance hours, storage, I/O operations
Remember: Perfect for data with complex relationships - think "anything with connections between entities."
Amazon Timestream
Type: Time-series database service
Performance: 1000x faster than relational databases for time-series
Use Case: IoT applications, DevOps monitoring, industrial telemetry
Cost Metric: Data ingestion, storage, queries
Think: "When your data is timestamp-based and you need to track changes over time at scale."
Data Migration & Integration
AWS Database Migration Service (DMS)
Purpose: Migrate databases to AWS with minimal downtime
Support: Homogeneous and heterogeneous migrations
Use Case: Database migration, continuous replication, data consolidation
Cost Metric: Compute resources used + data transfer
Remember: DMS can migrate between different database types (e.g., Oracle to Aurora) with Schema Conversion Tool (SCT).
AWS Glue
Type: Managed ETL (Extract, Transform, Load) service
Features: Data catalog, job scheduler, development endpoints
Use Case: Data preparation for analytics, unified data catalog
Cost Metric: Crawler runtime, ETL job duration, DPU-hours
Think: "Serverless data integration service that makes it easy to prepare data for analytics."

Key Exam Pattern: AWS provides specialized database solutions for different data types and usage patterns. Choose the right database based on:
  • Data structure (relational vs non-relational)
  • Access patterns (OLTP vs OLAP)
  • Scaling requirements
  • Serverless vs provisioned capacity
